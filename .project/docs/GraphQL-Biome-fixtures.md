## 1. Что Biome умеет по GraphQL

Biome работает с **исходниками GraphQL** (файлы `.graphql` / `.gql`): операции, фрагменты, при необходимости схема как документ. Это **не** проверка JSON-фикстур против схемы.

**Линт (правила):**
- **correctness:** `useGraphqlNamedOperations` — именованные операции.
- **style:** `useDeprecatedReason`, `useGraphqlNamingConvention` (enum в PascalCase).
- **suspicious:** `noDuplicateFields` в операциях.
- **nursery:** дубликаты имён (аргументы, enum, поля, переменные), `useLoneAnonymousOperation`, `useLoneExecutableDefinition`, и др.

**Форматирование:** Biome умеет форматировать GraphQL-документы (как Prettier для `.graphql`).

**Чего нет в Biome:** проверки, что **конкретный JSON (фикстуры, ответ API)** соответствует GraphQL-схеме или форме запроса. То есть «валидировать fixtures/context на совместимость с GraphQL» Biome сам по себе не делает.

## 2. Валидация fixtures/context на совместимость с GraphQL

У вас контекст собирается из:
- **fixtures** — JSON из `fixtures/*.json`, приводятся к `CanonicalContextInput`;
- **wpgraphql** — другой источник (WPGraphQL), тот же канонический контекст.

Чтобы **гарантировать совместимость фикстур с GraphQL**, нужна проверка формы данных против схемы или против формы запросов, а не линтер кода. Варианты:

1. **Схема + `graphql-js` (или аналог)**  
   Есть схема (SDL или интроспекция). Написать скрипт/тест, который:
   - загружает схему;
   - для каждого типа, который «поставляют» фикстуры (например, тип для меню, постов и т.д.), строит ожидаемую форму;
   - проверяет, что соответствующие куски `CanonicalContextInput` / JSON проходят валидацию (например, через `validateValue` или проверку полей/типов по схеме).

2. **Совпадение с формой запросов**  
   Если данные должны совпадать с тем, что возвращают реальные GraphQL-запросы:
   - храните запросы в `.graphql`;
   - линтите/форматируйте их через **Biome** (общие проверки GraphQL);
   - отдельно: скрипт/тест, который по тем же запросам (или по сгенерированным из них типам) проверяет, что структура фикстур совпадает с ожидаемой (например, те же поля и вложенность). Это можно делать через codegen (GraphQL Code Generator и т.п.) или ручной тип/контракт в TypeScript.

3. **Один канонический тип (TypeScript)**  
   У вас уже есть `CanonicalContextInput` и адаптеры. Можно:
   - считать «контрактом» этот тип (и при необходимости породить из него JSON Schema);
   - валидировать все фикстуры против этого контракта (например, через тип при загрузке + тесты, или через ajv/zod по сгенерированной схеме);
   - при этом считать, что этот контракт согласован с вашей GraphQL-схемой (вручную или через общую кодогенерацию). Тогда Biome не участвует в валидации данных, только в качестве линтера/форматтера для `.graphql` файлов.

## 3. Как сочетать Biome и валидацию fixtures/GraphQL

- **Biome в корне монорепо:**  
  - включить обработку `**/*.graphql` в `biome.json` (формат + линт GraphQL);
  - так вы получаете единый стиль и базовые проверки для всех операций/фрагментов.

- **Валидация фикстур на совместимость с GraphQL:**  
  - вынести в отдельный шаг: скрипт или тесты (например, в `packages/maintain` или в приложениях), которые:
    - читают схему и/или форму запросов;
    - проверяют, что `fixtures/*.json` (или объект context после адаптеров) соответствуют этой форме.
  - Biome здесь используется только для качества и консистентности самих `.graphql` файлов, а не для проверки JSON.

Итого: **контроль GraphQL в Biome** — это линт и формат документов `.graphql`. **Валидация fixtures/context на совместимость с GraphQL** делается отдельным инструментом (скрипт/тесты + схема или контракт типов), а Biome можно использовать рядом для поддержания качества самих запросов и схемы в репозитории.
